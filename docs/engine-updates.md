# Обновление общего ядра

## Источник

Engine, SDK и навыки собираются в ChiselCode из того же source commit, что и CLI. Release публикует `engine-manifest.json` с SHA-256 всех четырёх binaries, SDK и skills. Desktop принимает артефакты только указанного GitHub release; проверенные hashes записываются в Git.

## Версии

| Версия | Назначение |
|---|---|
| Desktop SemVer | Пользовательский выпуск и установщики |
| Engine version | Точный выпуск runtime, независимый от desktop |
| Protocol major/minor | Совместимость JSON DTO и методов |
| Session schema | Core storage/migration, не версия UI |
| Source commit + asset SHA-256 | Происхождение и точные байты встроенного ядра |

Смена engine patch сама по себе не требует изменения React. При добавлении метода/capability старый клиент сохраняет поддерживаемые сценарии. Удаление метода, изменение обязательного поля или несовместимое значение существующего enum требует нового protocol major либо совместимого перехода. SDK не является универсальной обещанной совместимостью любых будущих CLI.

## Рабочая процедура

Для агента действует [общий порядок синхронизации CLI и Desktop](https://github.com/TheAsrada/ChiselCode/blob/main/docs/contributors/desktop-sync.md), закреплённый в AGENTS.md обоих репозиториев. При изменении общего поведения необходимая адаптация клиента выполняется в том же задании. До просьбы о релизе новый engine отмечается как ожидающий выпуска в `Unreleased`, а lock сохраняет настоящий опубликованный набор. Просьба «сделай релиз» по умолчанию включает обе оболочки.

1. Выпустить ChiselCode с прошедшими runtime/CLI tests и compiled engine smoke на каждой целевой ОС.
2. Выполнить `npm run update:engine -- v<версия>`. Скрипт проверяет manifest, source commit, имена assets и поддерживаемый protocol major.
3. `npm run sync:engine` скачивает текущую платформу, SDK и skills, проверяет SHA-256. `npm ci` устанавливает точные клиентские зависимости.
4. `npm run verify`, `npm run test:e2e`; затем собрать installer и повторить GUI acceptance на его установленном payload.
5. Проверить существующие сессии, отказ/отмену, Plan и профиль подключения; для новых core features добавить подходящий сценарий.
6. Записать изменения в CHANGELOG: desktop поведение, новая engine version, совместимость/миграции. Commit lock и SDK-facing изменения вместе.
7. Выпустить desktop installer как единый проверенный набор. Не заменять системный CLI из desktop installer.

## Какие изменения переносятся легко

Новые обычные tools, исправления runtime, scheduler, drivers и провайдеров приходят с новым ядром; generic tool cards и динамический каталог не требуют копирования реализации. Новая специализированная панель, extension UI contribution или структура approval требует клиентской реализации и acceptance.

Кандидат с другим major отклоняется до запуска задач. При изменении схемы Session core обязан гарантировать чтение старого формата и явно определить совместимость старых writers. Downgrade после необратимой storage migration не обещается: сначала проверяется data reader floor и резервная копия в core, затем выпуск desktop. В текущей beta schemaVersion=3 сохраняется.

## Откат

Возвращать следует полный предыдущий desktop installer с его engine lock. Сохраняйте пользовательские данные и совместимый предыдущий release. Не делайте force push и не заменяйте опубликованные assets под прежним тегом; исправление получает новую версию. Если миграция не допускает старое ядро, откат UI не является откатом данных.

По поручению о релизе агент обновляет lock и выпускает обе оболочки по указанному порядку. Автоматического GitHub-бота для подписки на core releases сейчас нет. Будущая автоматизация не должна публиковать новый desktop без платформенных проверок и не требует PAT в пользовательском приложении.
